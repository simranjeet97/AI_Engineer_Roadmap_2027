# vLLM vs SGLang: A Deep Comparative Analysis of LLM Serving Schedulers

## 1. Why Does an LLM Engine Need a Scheduler?

Imagine you run a popular restaurant with one kitchen (the GPU). On a Friday night, 500 people show up wanting dinner at the same time. You need a **maître d'** — someone who decides:

1. **Who gets seated next** (which request gets GPU compute time)
2. **Which tables are available** (how to allocate KV cache memory)
3. **What happens when you're full** (how to handle preemption when memory runs out)

That maître d' is the **scheduler**. Without one, your kitchen burns down.

### Why Can't We Just Process Requests One at a Time?

Let's do some napkin math. A single request to a 70B parameter model might take ~2 seconds for a 200-token response. If 500 users are waiting:

$$T_{sequential} = 500 \times 2 = 1000 \text{ seconds} \approx 17 \text{ minutes}$$

User #500 waits 17 minutes. That's unacceptable. GPUs are also massively parallel — processing one request at a time wastes ~90% of the GPU's capacity.

**Batching** is the solution: serve multiple requests simultaneously. But batching introduces three hard problems:

### Problem 1: Who Gets GPU Time?

Not all requests arrive at the same time or need the same compute. Some are in the **prefill** phase (processing the entire input prompt — compute-heavy). Others are in the **decode** phase (generating one token at a time — memory-bandwidth-heavy). The scheduler must interleave these efficiently.

### Problem 2: KV Cache Memory Management

Every token generated by a Transformer creates a **Key-Value (KV) cache** entry. For a 70B model with 80 layers:

$$\text{KV cache per token} = 2 \times n_{layers} \times d_{head} \times n_{heads} \times \text{sizeof(fp16)}$$

For Llama 70B: $2 \times 80 \times 128 \times 64 \times 2 \text{ bytes} \approx 2.6 \text{ MB per token}$

A request generating 1000 tokens needs ~2.6 GB of GPU memory *just for KV cache*. With 500 concurrent requests, you'd need **1.3 TB** — far more than any GPU has.

The scheduler must decide: who gets memory, how much, and what happens when it runs out.

### Problem 3: Preemption — What Happens When Memory Runs Out?

Mid-generation, a request might need one more block of memory, but the GPU is full. You have two choices:

- **Recompute**: Kill the request's KV cache, free the memory, and later re-run the prefill from scratch
- **Swap**: Copy the KV cache to CPU RAM over PCIe, free GPU memory, and copy it back later

Both are expensive. The scheduler's intelligence determines which strategy minimizes total wasted work.

## 2. vLLM: The BlockManager Architecture

vLLM (Virtual LLM) was the first system to bring **virtual memory concepts** from operating systems into LLM serving. Its key insight: treat KV cache like pages in an OS virtual memory system.

### The Three Queues

vLLM's scheduler maintains three queues at all times:

```
┌─────────────────────────────────────────────────┐
│                  vLLM Scheduler                  │
│                                                  │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐      │
│  │ WAITING  │  │ RUNNING  │  │ SWAPPED  │      │
│  │  Queue   │  │  Queue   │  │  Queue   │      │
│  │          │  │          │  │          │      │
│  │ Req #5   │  │ Req #1   │  │ Req #3   │      │
│  │ Req #6   │  │ Req #2   │  │          │      │
│  │ Req #7   │  │ Req #4   │  │          │      │
│  └──────────┘  └──────────┘  └──────────┘      │
│       ▲              │              │            │
│       │         ┌────▼────┐         │            │
│       │         │  Block  │         │            │
│       └─────────│ Manager │─────────┘            │
│                 └─────────┘                      │
└─────────────────────────────────────────────────┘
```

- **Waiting**: New requests that haven't been allocated any GPU memory yet
- **Running**: Requests actively being processed on the GPU with allocated KV cache blocks
- **Swapped**: Requests whose KV cache was evicted to CPU RAM to make room for others

### The Scheduling Loop

Every iteration (every time the model generates one token for the batch), the scheduler runs this loop:

```python
def schedule_one_step():
    # Phase 1: Try to resume swapped-out requests
    while swapped_queue not empty:
        req = swapped_queue.front()
        if block_manager.can_swap_in(req):
            swap_in(req)           # copy KV cache back from CPU → GPU
            move req to running_queue
        else:
            break                  # not enough GPU blocks

    # Phase 2: Try to admit new requests from waiting queue
    while waiting_queue not empty:
        req = waiting_queue.front()
        if block_manager.can_allocate(req):
            allocate_blocks(req)   # reserve GPU blocks for this request
            move req to running_queue
        else:
            break                  # stop scheduling new requests

    # Phase 3: Ensure running requests can continue
    for req in running_queue:
        if req.needs_new_block():
            if block_manager.has_free_blocks():
                allocate_one_block(req)
            else:
                # PREEMPTION: pick a victim and evict it
                victim = running_queue.last()  # LIFO: newest request
                preempt(victim)                # swap or recompute
                allocate_one_block(req)
```

**Key design choice**: vLLM uses **FCFS (First-Come, First-Served)** ordering. The first request to arrive gets priority. This is simple and fair, but not always optimal.

### The Block Table: Virtual → Physical Mapping

Just like an OS maps virtual pages to physical frames, vLLM maps **logical blocks** to **physical blocks**:

```
Request #1 Block Table:
┌──────────────┬──────────────────┐
│ Logical Block│ Physical Block # │
├──────────────┼──────────────────┤
│      0       │       7          │
│      1       │       3          │
│      2       │      12          │
└──────────────┴──────────────────┘

Request #2 Block Table:
┌──────────────┬──────────────────┐
│ Logical Block│ Physical Block # │
├──────────────┼──────────────────┤
│      0       │       1          │
│      1       │       9          │
└──────────────┴──────────────────┘
```

Each block holds a fixed number of tokens' KV cache (typically 16 tokens per block). The physical blocks can be **anywhere** in GPU memory — they don't need to be contiguous. This eliminates fragmentation, just like virtual memory eliminates RAM fragmentation in operating systems.

### Prefix Caching in vLLM: Hash-Based Block Matching

vLLM supports prefix caching, but it works at **block granularity**. Here's how:

1. Each block of 16 tokens is hashed: `hash(token_ids[0:16])`, `hash(token_ids[0:32])`, etc.
2. The hash is computed **cumulatively** — block 2's hash includes all tokens from blocks 0, 1, and 2
3. When a new request arrives, vLLM checks: "Have I seen this exact sequence of tokens in a block before?"
4. If yes, the new request's block table points to the **same physical block** (copy-on-write)

```
Hash Table:
┌──────────────────────────┬──────────────────┐
│ hash(tokens[0:16])       │ Physical Block 7 │
│ hash(tokens[0:32])       │ Physical Block 3 │
│ hash(tokens[0:48])       │ Physical Block 12│
└──────────────────────────┴──────────────────┘
```

**Limitation**: Matching only works at block boundaries. If your shared prefix is 20 tokens long but blocks are 16 tokens, only the first block (16 tokens) is shared. The remaining 4 tokens must be recomputed.

### Preemption Strategies

When memory runs out, vLLM picks a **victim** (typically the most recently added request — LIFO order) and uses one of two strategies:

| Strategy | How It Works | Cost | When Used |
|----------|-------------|------|-----------|
| **Recompute** | Delete victim's KV cache, re-prefill later | Wasted prefill compute | Short prefills, no swap space |
| **Swap** | Copy KV cache to CPU RAM via PCIe | PCIe bandwidth (~32 GB/s) | Long prefills worth saving |

**Example**: Request #3 has generated 200 tokens ($200 \times 2.6\text{ MB} = 520\text{ MB}$ of KV cache). Swapping 520 MB over PCIe Gen4 x16 at 32 GB/s takes:

$$T_{swap} = \frac{520 \text{ MB}}{32 \text{ GB/s}} \approx 16 \text{ ms}$$

That's fast enough to be worthwhile — recomputing 200 tokens of prefill would take much longer.

### Concrete Example: 3 Requests, 10 Physical Blocks

Let's say each block holds 16 tokens and we have 10 physical blocks on the GPU.

| Request | Prompt Tokens | Blocks Needed (Prefill) |
|---------|--------------|------------------------|
| Req A   | 40 tokens    | $\lceil 40/16 \rceil = 3$ blocks |
| Req B   | 30 tokens    | $\lceil 30/16 \rceil = 2$ blocks |
| Req C   | 55 tokens    | $\lceil 55/16 \rceil = 4$ blocks |

**Step 1**: Scheduler processes waiting queue (FCFS order: A, B, C).

```
Allocate Req A: blocks 0,1,2 → running     (3/10 used)
Allocate Req B: blocks 3,4   → running     (5/10 used)
Allocate Req C: blocks 5,6,7,8 → running   (9/10 used)
Free blocks remaining: 1
```

**Step 2**: All three requests start decoding. Each generates tokens. After Req A generates 16 tokens, it needs a 4th block. Block 9 is allocated. **Free blocks: 0.**

**Step 3**: Req B generates 16 tokens and needs a 3rd block. No free blocks! **Preemption triggered.**

```
Victim: Req C (LIFO — most recently admitted)
Strategy: Swap Req C's 4 blocks to CPU RAM
Free blocks recovered: 4 (blocks 5,6,7,8)
Allocate block 5 to Req B.
Req C moves to swapped_queue.
```

**Step 4**: Later, when Req A or B finishes and frees blocks, Req C is swapped back in.

## 3. SGLang: The RadixCache Architecture

SGLang takes a fundamentally different approach. Instead of flat block tables, it uses a **radix tree** (a type of trie) to store and share KV cache across requests.

### What Is a Trie? (First Principles)

A **trie** (pronounced "try") is a tree data structure where each path from root to leaf represents a sequence. Let's start with a simple string example:

```
Storing: "cat", "car", "card", "dog"

         (root)
        /      \
       c        d
       |        |
       a        o
      / \       |
     t   r      g
         |
         d

To find "car": root → c → a → r ✓ (found!)
To find "cap": root → c → a → ? (no 'p' child — not found!)
```

The magic: **shared prefixes are stored only once**. "cat", "car", and "card" all share the "ca" path. This saves memory and makes prefix lookups O(length) — blazingly fast.

### A Radix Tree Is a Compressed Trie

A **radix tree** collapses chains of single-child nodes into one node:

```
Regular trie:          Radix tree:
    (root)               (root)
   /      \             /      \
  c        d          "ca"    "dog"
  |        |          /  \
  a        o        "t"  "r"
 / \       |              |
t   r      g             "d"
    |
    d
```

Fewer nodes = less memory overhead and faster traversal.

### How SGLang Uses a Radix Tree for KV Cache

In SGLang, the radix tree stores **token sequences** instead of character strings. Each node holds:

1. The **token IDs** for that segment of the path
2. Pointers to the **physical KV cache blocks** storing those tokens' keys and values
3. A **reference count** (how many active requests use this node)
4. A **last access timestamp** (for LRU eviction)

```
                        (root)
                          |
              ┌───────────┴───────────┐
              ▼                       ▼
     [System Prompt: 500 tokens]   [Other prefix...]
     KV blocks: [B0, B1, B2, ...]  
     ref_count: 3
              |
     ┌────────┼────────┐
     ▼        ▼        ▼
  ["What    ["Explain  ["What
   is        recursion"  is
   Python?"  8 tokens]   Python?"
   5 tokens]             5 tokens]
  KV: [B32]  KV: [B33]  
  ref: 1     ref: 1     ref: 1
```

**Critical insight**: Request 3 ("What is Python?") asks the same question as Request 1. SGLang's radix tree detects this immediately — the path already exists! Request 3 can **reuse the entire KV cache** from Request 1, including the answer tokens generated so far.

### Prefix Matching: How It Works Step by Step

When a new request arrives with tokens `[t0, t1, t2, ..., tN]`:

```python
def find_prefix_match(token_ids):
    node = root
    matched_tokens = 0

    while matched_tokens < len(token_ids):
        # Look for a child whose edge starts with the next token
        next_token = token_ids[matched_tokens]
        if next_token in node.children:
            child = node.children[next_token]
            edge_tokens = child.edge_tokens

            # Check how many tokens along this edge match
            match_len = 0
            while (match_len < len(edge_tokens) and
                   matched_tokens + match_len < len(token_ids) and
                   edge_tokens[match_len] == token_ids[matched_tokens + match_len]):
                match_len += 1

            matched_tokens += match_len

            if match_len < len(edge_tokens):
                # Partial match — split this node
                break
            node = child
        else:
            break  # No matching child

    return matched_tokens  # Number of tokens we can skip prefilling
```

**This matching is arbitrary-length** — not block-aligned like vLLM. If 137 tokens match, you skip exactly 137 tokens of prefill. No waste.

### LRU Eviction on Unreferenced Leaves

When GPU memory is full, SGLang evicts leaf nodes with `ref_count = 0` (no active request uses them), starting with the **Least Recently Used**:

```
Before eviction (memory full):

         (root)
           |
    [System Prompt]     ← ref_count: 2 (Req 1 & 2 using it)
      /         \
  [Q: Python]  [Q: Recursion]
  ref: 0        ref: 1
  last_use:     last_use:
  10:30:01      10:30:05
     ▲
     │
  EVICT THIS FIRST
  (ref_count=0, oldest last_use)
```

After eviction, the "What is Python?" leaf is removed and its KV cache blocks are freed. The system prompt node remains because it still has active references.

### Full ASCII Diagram: 3 Conversations Sharing a System Prompt

```
                              ┌──────────┐
                              │   ROOT   │
                              └────┬─────┘
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                              ▼
        ┌───────────────────────┐     ┌───────────────────────┐
        │ "You are a helpful    │     │ "Summarize the        │
        │  AI assistant. Answer │     │  following document:" │
        │  questions clearly."  │     │  (200 tokens)         │
        │  (500 tokens)         │     │  KV: [B50..B62]       │
        │  KV: [B0..B31]       │     │  ref_count: 1         │
        │  ref_count: 3         │     └───────────┬───────────┘
        └──────┬────────────────┘                  │
               │                          ┌────────┴────────┐
    ┌──────────┼──────────┐               ▼                 ▼
    ▼          ▼          ▼        [Doc chunk A]     [Doc chunk B]
┌────────┐┌────────┐┌────────┐    ref: 1            ref: 1
│ Req 1  ││ Req 2  ││ Req 3  │
│"What is││"Explain││"What is│
│Python?"││recurs."││Python?"│

│KV:[B32]││KV:[B33]││ → B32! │ ← Points to SAME block as Req 1!
│ref: 1  ││ref: 1  ││ref: 1  │
└────────┘└────────┘└────────┘
```

Notice: Req 3 doesn't allocate new KV blocks — it references B32 directly. **Zero prefill compute, zero additional memory.**

## 4. Head-to-Head Comparison

| Dimension | vLLM | SGLang |
|-----------|------|--------|
| **KV cache data structure** | Flat block table per request | Global radix tree (shared trie) |
| **Prefix matching granularity** | Block-aligned (e.g., 16-token boundaries) | Arbitrary token-level |
| **Multi-turn efficiency** | Limited — must hash & lookup per block | Excellent — tree naturally extends conversations |
| **Eviction policy** | Preempt entire request (LIFO) | LRU on unreferenced leaf nodes (fine-grained) |
| **Memory overhead of metadata** | Low — one flat array per request | Higher — tree nodes + edges + ref counts |
| **Scheduling heuristic** | FCFS (First-Come First-Served) | LPM (Longest Prefix Match first) |
| **Prefix sharing** | Copy-on-write blocks via hash table | Structural sharing via tree pointers |
| **Workload sweet spot** | Independent, diverse requests | Repeated prefixes, multi-turn, agentic |
| **Preemption mechanism** | Swap to CPU or recompute | Evict LRU leaves, keep shared nodes |
| **Complexity** | Simpler to reason about | More complex tree operations |

### Deeper Analysis of Key Differences

**FCFS vs LPM Scheduling**

vLLM processes requests in arrival order. SGLang is smarter — it prioritizes the request with the **Longest Prefix Match** in the cache:

```
Cache currently holds: "You are a helpful AI assistant."

Waiting queue:
  Req A (arrived first):  "Tell me a joke about cats"       → 0 token match
  Req B (arrived second): "You are a helpful AI assistant.   → 500 token match!
                           Explain quantum computing."

vLLM schedules: Req A first (FCFS)         → 0 tokens saved
SGLang schedules: Req B first (LPM)        → 500 tokens saved
```

By scheduling Req B first, SGLang skips 500 tokens of prefill compute. That's not just a memory win — it's a **latency** win because prefill is the most compute-intensive phase.

**Eviction Granularity**

When memory pressure hits:

- **vLLM**: Must preempt an **entire request** — all its blocks are swapped or recomputed. This is coarse-grained and can waste significant work.
- **SGLang**: Evicts individual **leaf nodes** that no active request references. Shared internal nodes (like the system prompt) are protected by their reference counts. This is surgical.

## 5. When to Choose Which

### Decision Matrix

| Workload Pattern | Recommendation | Why |
|-----------------|----------------|-----|
| Independent single-turn requests (diverse prompts) | **vLLM** | Simpler scheduling, less metadata overhead. Few shared prefixes to exploit. |
| Multi-turn chat with shared system prompts | **SGLang** | Radix tree naturally shares the system prompt across all conversations. Tree extends as conversation grows. |
| Agentic loops with branching (e.g., tree-of-thought) | **SGLang** | Branching creates shared prefixes. Radix tree stores branches efficiently. vLLM would duplicate KV cache for each branch. |
| RAG with common document prefixes | **SGLang** | Multiple queries over the same retrieved document chunk share the prefix. SGLang caches it once. |
| Raw throughput benchmark (independent, non-overlapping) | **Roughly equal** | With no prefix sharing opportunity, SGLang's tree overhead doesn't help. Both achieve similar throughput. |
| Low-memory environments | **vLLM** | Lower metadata overhead. Swap-to-CPU provides a safety valve. |
| High request diversity (every prompt is unique) | **vLLM** | The radix tree overhead provides no benefit when nothing is shared. |

### Rule of Thumb

> **If your requests share prefixes → SGLang. If they don't → vLLM.**
>
> In production, most LLM applications (chatbots, agents, RAG) *do* share prefixes
> (system prompts, document contexts), which is why SGLang often wins in real-world
> deployments.

## 6. Concrete Worked Example

Let's trace the **exact same workload** through both engines and count operations.

### The Workload

All three requests share a system prompt (500 tokens), followed by different user messages:

| Request | System Prompt | User Query | Total Tokens |
|---------|--------------|------------|-------------|
| Req 1   | 500 tokens   | "What is Python?" (5 tokens) | 505 |
| Req 2   | 500 tokens   | "Explain recursion" (8 tokens) | 508 |
| Req 3   | 500 tokens   | "What is Python?" (5 tokens) | 505 |

Assume: block size = 16 tokens, so the 500-token system prompt spans $\lceil 500/16 \rceil = 32$ blocks.

---

### How vLLM Handles This

**Step 1: Req 1 arrives**

```
Hash lookup: No cached blocks found.
Allocate: 32 blocks for system prompt + 1 block for user query = 33 blocks
Prefill: ALL 505 tokens (full computation)
Tokens prefilled: 505
```

With prefix caching enabled, vLLM hashes each block:
```
hash(tokens[0:16])   → Block P0
hash(tokens[0:32])   → Block P1
...
hash(tokens[0:496])  → Block P30
hash(tokens[0:505])  → Block P31  (partially filled: 505 - 496 = 9 tokens)
                                   Wait — this crosses into user tokens!
```

Actually, let's be precise. The system prompt (500 tokens) fills:
- Blocks 0–30: fully filled (31 × 16 = 496 tokens)
- Block 31: partially filled (4 system prompt tokens + 5 user tokens = 9 tokens)

vLLM hashes blocks 0–30 individually. Block 31 mixes system and user tokens, so its hash is unique to this request.

**Step 2: Req 2 arrives**

```
Hash lookup for blocks 0–30: ALL HIT! (same system prompt)
Block 31: MISS (different user query: "Explain recursion" ≠ "What is Python?")
Reuse: 31 blocks (496 tokens of KV cache shared via copy-on-write)
Allocate: 1 new block for remaining 12 tokens (4 system + 8 user)
Prefill: only 12 tokens (the 4 remaining system tokens + 8 user tokens)
Tokens prefilled: 12
```

Wait — vLLM's prefix caching is block-aligned and cumulative. The hash for block 31 depends on ALL preceding tokens plus the tokens in block 31. Since the first 496 tokens are identical, blocks 0–30 match. Block 31 contains tokens 496–507 for Req 1 vs tokens 496–507 for Req 2. Tokens 496–499 are identical (same system prompt), but token 500+ differs. So block 31 does NOT match.

**Corrected: Req 2 reuses 31 blocks (496 tokens), prefills 12 tokens.**

**Step 3: Req 3 arrives**

```
Hash lookup for blocks 0–31: ALL HIT! (identical to Req 1 — same prompt + same query)
Reuse: ALL 32 blocks
Prefill: 0 tokens — exact match found for the full 505 token sequence!

Wait — 505 tokens span 32 blocks (31 full + 1 partial with 9 tokens).
Block 31 hash for Req 3 = hash(tokens[0:505]) — same as Req 1!
So yes, full cache hit.
Tokens prefilled: 0 (but only 505 tokens matched, for the partial block)
```

Hmm, let's be more careful. 505 tokens across 16-token blocks:
- Blocks 0–31: 32 blocks × 16 = 512 token slots, but only 505 are filled
- Block 31 has 505 - (31 × 16) = 505 - 496 = 9 tokens

For Req 3 (identical to Req 1), all blocks 0–31 hash-match. **Prefill: 0 tokens.**

**vLLM Total Prefill Summary:**

| Request | Tokens Prefilled | Tokens Reused |
|---------|-----------------|---------------|
| Req 1   | 505             | 0             |
| Req 2   | 12              | 496           |
| Req 3   | 0               | 505           |
| **Total** | **517**       | **1001**      |

Without prefix caching, total would be $505 + 508 + 505 = 1518$ tokens.

**Savings**: $1518 - 517 = 1001$ tokens saved ($65.9\%$ reduction).

### How SGLang Handles This

**Step 1: Req 1 arrives**

```
Radix tree lookup from root: empty tree, no match.
Insert path: [system_prompt_500_tokens] → [user_query_5_tokens]
Prefill: ALL 505 tokens
Tree state:

    (root)
      │
  [System prompt: 500 tokens]  ← ref_count: 1
      │
  ["What is Python?": 5 tokens]  ← ref_count: 1
```

Tokens prefilled: **505**

**Step 2: Req 2 arrives**

```
Radix tree lookup: traverse from root
  → [System prompt: 500 tokens] MATCH! (500 tokens matched)
  → children: ["What is Python?"] — first token doesn't match "Explain"
  → Match length: 500 tokens (NOT block-aligned — exactly 500!)

Skip prefill for 500 matched tokens.
Insert new branch: ["Explain recursion": 8 tokens]
Prefill: only 8 tokens (the user query)
```

```
Tree state:

        (root)
          │
    [System prompt: 500 tokens]  ← ref_count: 2
        /              \
["What is Python?"  ["Explain recursion"
  5 tokens]           8 tokens]
  ref: 1              ref: 1
```

Tokens prefilled: **8**

**Step 3: Req 3 arrives**

```
Radix tree lookup: traverse from root
  → [System prompt: 500 tokens] MATCH!
  → ["What is Python?": 5 tokens] MATCH! (exact same query as Req 1)
  → Match length: 505 tokens — FULL MATCH!

Skip ALL prefill. Just increment ref_count.
Prefill: 0 tokens
```

```
Tree state:

        (root)
          │
    [System prompt: 500 tokens]  ← ref_count: 3
        /              \
["What is Python?"  ["Explain recursion"
  5 tokens]           8 tokens]
  ref: 2              ref: 1
```

Tokens prefilled: **0**

**SGLang Total Prefill Summary:**

| Request | Tokens Prefilled | Tokens Reused |
|---------|-----------------|---------------|
| Req 1   | 505             | 0             |
| Req 2   | 8               | 500           |
| Req 3   | 0               | 505           |
| **Total** | **513**       | **1005**      |

---

### Side-by-Side Comparison

| Metric | vLLM (Prefix Cache) | SGLang (RadixCache) | SGLang Advantage |
|--------|--------------------|--------------------|-----------------|
| Req 1 prefill | 505 tokens | 505 tokens | — |
| Req 2 prefill | 12 tokens | 8 tokens | **4 fewer tokens** |
| Req 3 prefill | 0 tokens | 0 tokens | — |
| **Total prefill** | **517 tokens** | **513 tokens** | **4 fewer tokens** |
| Req 2 reuse | 496 tokens (block-aligned) | 500 tokens (exact) | **4 more tokens reused** |

Where does the 4-token difference come from? vLLM's prefix cache is **block-aligned**. The system prompt is 500 tokens, but $500 \mod 16 = 4$. Those 4 trailing tokens in the partial block couldn't be shared because the rest of that block contained different user query tokens. SGLang's radix tree matched all 500 system prompt tokens exactly.

**In larger workloads, this difference compounds.** Imagine 10,000 requests with a 500-token system prompt:

$$\text{vLLM wasted tokens} = 10{,}000 \times 4 = 40{,}000 \text{ extra prefill tokens}$$

At ~1ms per prefill token on an A100, that's 40 seconds of wasted GPU time.

## 7. Key Takeaways

1. **The scheduler is the brain of an LLM serving engine.** It decides who gets GPU time, manages KV cache memory (the most precious resource), and handles preemption gracefully. A bad scheduler can cut throughput by 5–10×.

2. **vLLM uses an OS-inspired virtual memory model.** Flat block tables map logical blocks to physical blocks. Prefix caching uses hash-based exact block matching. Preemption swaps or recomputes entire requests. It's simple, battle-tested, and works well for diverse, independent requests.

3. **SGLang uses a radix tree for structural KV cache sharing.** Token sequences form paths in a global trie. Prefix matching is automatic and token-level granular (not block-aligned). LRU eviction targets unreferenced leaves, preserving shared internal nodes. This shines for multi-turn chat, shared system prompts, and agentic workloads.

4. **The key architectural trade-off is simplicity vs sharing efficiency.** vLLM's block table is O(1) lookup but shares only at block boundaries. SGLang's radix tree is O(prefix_length) lookup but shares at arbitrary token boundaries.

5. **SGLang's LPM (Longest Prefix Match) scheduling is smarter than FCFS** for prefix-heavy workloads. By prioritizing requests that hit the cache, it maximizes reuse and minimizes total prefill compute.

6. **In practice, most production workloads favor SGLang's approach** because system prompts, RAG contexts, and multi-turn history naturally create shared prefixes. The 4-token-per-request savings from exact matching compounds to significant GPU time savings at scale.

7. **Choose vLLM** when requests are diverse with minimal prefix overlap, when you need swap-to-CPU as a safety valve, or when operational simplicity matters. **Choose SGLang** when you have shared system prompts, multi-turn conversations, agentic branching, or RAG workloads with repeated document chunks.

8. **Both engines are evolving rapidly.** vLLM is adding more sophisticated prefix caching, and SGLang is optimizing tree operations. The architectural ideas — paged KV cache vs radix-tree KV cache — are more important than any specific version's benchmarks.
